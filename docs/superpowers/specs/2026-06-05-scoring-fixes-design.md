# Scoring Fixes — Design Spec

**Date:** 2026-06-05  
**Status:** Approved

## Goal

Fix two scoring model defects that cause noise to outscore real pain:  
1. `dolorScore` weights frequency, not specificity — 27 broad noise signals beats 4 targeted pain signals.  
2. `has_deadline` in `GnewsSegmentConfig` is LLM-hallucinated — "autónomos en general" gets full urgency score.

---

## Fix 1: `dolorScore` specificity multiplier

### Problem

`dolorScore` formula: `dolor = freqScore * 0.5 + intensity * 0.5`

The gnews collector passes a signal through if it has any negative sentiment word (`sent ≤ -0.03`), even with `pain_keywords = []`. Broad queries return many signals with empty `pain_keywords`. `freqScore = min(n/20, 1) * 10` rewards raw count, so noise inflates scores.

### Fix

Add a specificity multiplier derived from the existing `pain_keywords` field — no signature change needed.

```typescript
const withKeywords = recent.filter(s => s.pain_keywords.length > 0).length;
const specificity = recent.length > 0 ? withKeywords / recent.length : 0;
const dolor = Math.min(
  Math.round((freqScore * 0.5 + intensity * 0.5) * Math.max(0.3, specificity) * 100) / 100,
  10.0,
);
```

A signal with `pain_keywords = []` (pure sentiment noise) contributes to the raw score but the whole segment gets discounted to a minimum of 30%.

**Example outcomes:**
- autónomos genérico: 27 signals, ~3 keyword matches → `specificity ≈ 0.11 → multiplier = 0.3` → noise discounted
- dentistas/verifactu: 4 signals, 4 keyword matches → `specificity = 1.0 → multiplier = 1.0` → no penalty
- gestores/SII: 0 signals → `dolor = 0` regardless (unchanged)

The 0.3 floor prevents over-penalizing thin but real segments where some signals lack keyword matches due to article phrasing.

## Fix 2: `has_deadline` whitelist

### Problem

`GnewsSegmentConfig.has_deadline` is generated by the LLM. The LLM assigns `has_deadline: true` to broad segments like "autónomos en general" which have no specific regulatory deadline, giving them full urgency score (10).

### Fix

Remove `has_deadline` from `GnewsSegmentConfig`. Add a deterministic whitelist check in `domain/rules.ts`.

```typescript
export const DEADLINE_KEYWORDS: string[] = [
  'verifactu', 'ticketbai', 'sii', 'rrsif', 'facturación electrónica',
  'factura electrónica', 'lexnet', 'docentia', 'aneca', 'sexenio',
  'visado electrónico', 'certificado energético', 'iva', 'irpf',
  'modelo 347', 'modelo 390',
];

export function hasRegulatoryDeadline(keywords: string[]): boolean {
  return DEADLINE_KEYWORDS.some(d =>
    keywords.some(k => new RegExp(`\\b${d}\\b`, 'i').test(k))
  );
}
```

Word-boundary regex prevents `iva` matching "motivación" or "derivado".

`runMarketTest` calls `urgencyScore(hasRegulatoryDeadline(config.keywords))` instead of `urgencyScore(config.has_deadline)`.

The LLM prompt in `market-test.ts` is updated to no longer request `has_deadline`.

### BOE fetcher (future)

The whitelist is a first cut. If a market test produces a suspicious `has_deadline: false` for a segment known to have a regulatory deadline, the BOE RSS fetcher (`checkBoeDeadline`) is the next step. The whitelist will identify exactly which entry is missing.

## Files Changed

| File | Change |
|------|--------|
| `domain/rules.ts` | Add `DEADLINE_KEYWORDS`, `hasRegulatoryDeadline` |
| `domain/scoring.ts` | Add specificity multiplier to `dolorScore` |
| `domain/types.ts` | Remove `has_deadline` from `GnewsSegmentConfig` |
| `infrastructure/collectors/gnews.ts` | `has_deadline: false` (no longer from config) |
| `infrastructure/config.ts` | Remove `has_deadline` from 4 `collectors.gnews.segments.*` defaults |
| `application/market-test.ts` | Strip `has_deadline` from LLM prompt; call `hasRegulatoryDeadline` |
| `test/unit/scoring.test.ts` | Update `dolorScore` tests; add specificity edge cases |

`SegmentConfig` (main pipeline, `synthesis_segments.*`) is unchanged — its `has_deadline` comes from config, not LLM.

---

## Out of Scope

- BOE RSS fetcher (first cut uses whitelist)
- `volumeScore` fix (separate concern)
- `DEFAULT_COMPETENCIA_SCORE` (known weakness, separate concern)
- Changes to `runScore`, `runCollect`, or any existing route
